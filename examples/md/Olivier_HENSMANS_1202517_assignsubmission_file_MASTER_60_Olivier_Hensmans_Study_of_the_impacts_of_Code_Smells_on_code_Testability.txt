 Résumé
Les Code Smells ont été étudiés depuis plus de 20 ans maintenant. Ils sont utilisés pour décrire intuitivement
une mauvaise implémentation de design dans un programme. Dans cette étude, nous souhaitons identier les
impacts de certains de ces Code Smells.    Et plus spéciquement, leur impacts potentiels sur la Testabilité.
Pour ce faire, nous allons étudier le champ des recherches scientiques sur les deux concepts que sont les Code
Smells et la Testabilité. Ces recherches nous permettrons de dénir les paramètres utilisés pour quantier les
concepts. Avec ces informations, nous analyserons la distribution statistique de nos échantillons et essaierons
de comprendre la relation entre les Code Smells et la testabilité sur un corpus de projets Java.


Mots-clés : Code Smells, Testabilité, Etude d'impact, Mesure du code



 Abstract
Code Smells have been studied for more than 20 years now. They are used to describe a design aw in a program
intuitively. In this study, we wish to identify the impact of some of these Code Smells. And, more specically,
their potential impact on Testability. To do this, we will study the state of the research on both Code Smells
and Testability. Using those studies, we will dene a scope of parameters to dene the two concepts. With that
information, we will analyse the statistical distribution of our samples and try to understand the relationship
between Code Smells and Testability in a corpus of Java projects.


Keywords : Code Smells, Testability, Impact Study, Code Metrics

Introduction
Code Smells are lousy patterns in a code, bad structural constructions of the abstraction. Their usage is against
the coding conventions. In this study, we want to understand if there is a relationship between those dierent
anti-patterns and the eort needed to test the code.


   At rst glance, it seems obvious that the bad usage of basic coding concepts might make tests harder to
implement. However, is it the case? This is our research question.


   In order to nd an answer to that question, we will rst dene the concept of Code Smells. We will uncover
and explain in detail some Code Smells that were found in studies to have a link with the Testability.


   We will then expose the state of the research on dening those concepts into metrics we can use to detect
Code Smells. We will also look for more explanation about what could inuence the denition, the detection
and the criticality of the Code Smells.


   Our second concept is Testability: intuitively, the ease of testing a code. We will examine its denition and
how the researchers have analysed the concept. After explaining the way we will consider the Testability in our
study, we will translate the concept into code metrics. We will also check if a study exists about the relationship
between Code Smells and other Testability characteristics such as the tests' eectiveness.


   These items will allow us to understand the two concepts, and we will be able to declare the scope of our
analysis :


    The corpus of projects we will inspect

    The Code Smells that we have selected and why

    The Translation of the Code Smells into metrics and their threshold

    The denition of the metrics for the Testability

   We then explain the chosen methodology to transform our metrics into usable data: parsing the raw XML
generated from the detection tools to a SQL database.      We will then describe our data populations and the
processing we will carry out to extract all their information. We will draw conclusions about the relationship
between the Code Smells studied and Testability using this information.


   We will then describe the results of our analysis and conclude on the possible threats it contains and the
next step it prepares.

3.1 Introduction to Code Smells
Since the mid-nineties, the issue of quality evaluation of object-oriented systems has been raised. More speci-
cally, the way we write source code aects the quality of the software. Multiple factors can explain the quality
issue in software engineering[16]. We can mention some of them :


    Software design is something abstract. Therefore, comparing its output with the expected one is complex.

    Writing Code depends on the specication which in turn depends on the stakeholders of the software.
      This means a direct dependency on human communication which always increases the complexity.


    Software are meant to evolve continuously over time. Each update can lead to a degradation of the design
      and an increase in complexity, resulting in an exponential decrease in quality and the need to continuously
      rethink the software design.


   In 1999, Fowler [6] identied patterns he named   bad smells in code. The idea was to identify and dene faulty
structures, names, practices, responsibilities, and dependencies. This set would become the set of potentially
faulty patterns. These denitions were based on practical experience in the eld, with no scientic study of the
real impact of those patterns on software quality. In his book, Fowler dened 22 patterns or structures in the
code, characterized them, and proposed mitigation or refactoring methods.
Some classic examples of code smells, and their impacts are :


    Duplicated Code: same code structure in more than one place, Fowler [6, p. 63] argues that by refactoring
      it, the program would be better with a unied structure.


    Long Method:      Fowler [6, p. 64] explains that making shorter methods make programs live better and
      longer.


   The term     Code Smells is now associated in the developer community with a design aw which impacts the
readability, maintainability and proneness to bugs in the code[10].


   Nevertheless, a more recent research study by Zhang et al [19] shows that those impacts do not exist for
Code Smells or at least not for all the 22 patterns. Another research [14] expresses that existing studies on these
impacts need to be more consistent and can not prove the existence of these impacts. Our study will attempt
to partially ll this gap.




3.2 Denition of Code Smells
In order to work on the Code Smells, we need to dene some of those concepts. There are many of them. We
will only dene those we are speaking about in this work. We invite the reader interested in the other Code
Smells to refer to the work from Fowler [6] and also from Lanza & Marinescu [10].

3.2.1 Duplicated Code or Code Clones
The Duplicated Code or Code Clones can be detected at all the levels of source code. It is one of the Code
Smells with the easiest concept to understand. It shows the same code structure in more than one place.


   This design is a complete violation of the Object Oriented design that looks for the reusability of the code
instead of duplication.


   Furthermore, having the same code at dierent places means that when we need to update that code, we
must update it in dierent places. It makes the evolution and maintainability of the source code much more
dicult[6].



3.2.2 Long Method
The Long Method can be detected at the method level but can also exist at the class level and is called Long
Class. It is exactly what it is called: a too-long method.


   Too many lines of code are bad for readability and understandability[6]. It is easier to deal with a few lines
of code than with hundreds.



3.2.3 Blob or God Class
The God Class, also named Blob, can be detected at the class level. It can be dened as "A large class imple-
menting dierent responsibilities and centralizing most of the system processing"[8].


   One primary concept of Object Oriented language "is that one class should have one responsibility"[10,
p. 80]. Having multiple responsibilities creates many issues as complexity or understandability.


   The reusability of the code is also an essential concept in Object Oriented languages. The issue with that
Smell is that when a class has all the responsibilities and delegates only a few to the other classes, it will be
hard to understand and complicated to reuse. That complication also means that developers will be tempted
to clone a part of the source code of the class instead of reusing it [6, p. 65], creating another Code Smells (see
Duplicated Code).


   Going further, software, in its life cycle, will evolve. The God Class will make that evolution much more
complicated.


   In other words, it brings complexity and bad understandability and is complicated to reuse and evolve.



3.2.4 Conditional Complexity
The Conditional Complexity can be detected at the method level. Conditions in the code are used to create a
new behaviour, e.g.   if you have that value, then do an action; otherwise, do another action.
   A method with too many "if" and "switch" statements leads to a duplication problem. Polymorphism should
be used in those cases. It is even worst with switches. They create even more possible behaviours with their
numerous dierent conditions.


   Having many conditions will create a large method and could increase the complexity and lower the under-
standability given the number of paths data could take given its value.


   Through Polymorphism, we create a new class that inherited the behaviours of the rst class at which we add
new specic behaviours. We could call our new class with the shared behaviours from the "mother" class and
the specic behaviours we seek instead of calling it through a class with many forks and paths. Furthermore,
not using that design, and working in only one class, often mean that we need to duplicate code to ensure some
shared behaviour in the dierent paths taken.

CHAPTER 3. CODE SMELLS                                                  3.2. DEFINITION OF CODE SMELLS

3.2.5 Complex Class
The Complex Class can be detected at the class level. This is a class with a high Cyclomatic Complexity and
very large in terms of Line of Code, a large class including too many independent running paths or branches
and too many loops.


   There is no need to explain why many lines of code could be bad for readability, understandability and the
ability to evolve the source code. It is easier to deal with a few lines of code than with hundreds.


   However, the Complex Class is more than a large class. It also brings complexity through the existence of a
great number of conditions and loops. It contains Conditional Complexity in its methods. There are multiple
paths that data could take into the class depending on its value.



3.2.6 Feature Envy
The Feature Envy can be detected at the method level. "A method is more interested in a class other than the
one it actually is in"[8].


   This method will look for data on many other classes to realize its purpose.    It envies other classes. It is an
issue because a class is supposed to be a package that contains data and its treatment. It is a logical unit.


   Other classes must always extract some data from a class to make the system work properly.             After all,
we need to know which client is linked to an account, but it shows a bad design when it happens too often.
When there is a Feature Envy, we break this logical unit, which makes it dicult to understand what is being
done with the data and how the code behaves. The mutual dependency between classes with the data and its
treatment makes it harder to read, understand, and maintain.



3.2.7 High Coupling
The High Coupling can be detected at the class level. It is a class that a lot of other classes will access. The
class is needed by many classes, creating lots of dependencies on our High Coupling class.


   As described above, it is an issue because a class is supposed to be a package that contains data and its
treatment. Therefore, it is a logical unit. A class gathering many responsibilities, it is the opposite. As for the
Feature Envy, the mutual dependency between classes with the data and its treatment makes it harder to read,
understand, and maintain.



3.2.8 Message Chain
The Message Chain can be detected at the method level. "You see message chains when a client asks one object
for another object, which the client then asks for yet another object, which the client then asks for yet another
object, and so on. Navigating in this way means that the client is coupled to the structure of the navigation.
Any change to the intermediate relationships causes the client to have to change."[19]


   Suppose a method uses a sequence of calls to other objects to perform its processing. In that case, it creates
a direct dependency on the denition of the relationship between each sequence element. For example,      imagine
a method A that calls the object B, make treatment and calls the object C on the data made with that treatment
to get another data that will be treated with the help of the object D. In order to ensure that the sequence work,
we need to have data structure denitions and treatments in each object to match between themselves. They
have a high dependency.
3.2. DEFINITION OF CODE SMELLS                                                 CHAPTER 3. CODE SMELLS

3.2.9 Shotgun Surgery
The Shotgun Surgery can be detected at the method level. Every time we change the method, we must make
many little changes to many dierent classes.


   It is a dependency from the inside to the outside of the method but also the other way around.         These
dependencies make it more dicult to evolve the source code. As a result, there is always a risk of missing a
change and creating faults and bugs.



3.2.10 Spaghetti Code
The Spaghetti Code can be detected at the class level. It is a class with complex methods interacting between
them with global variables.


   This Code Smells often appears in software evolution when there is very little software structure, and many
people are working on that evolution. It results in a code with high complexity and unclear relationship between
the methods.


   Global variables are used to share data with other methods. That process makes it more complicated to
understand the sequence of change of those variables. Everyone works on their part, producing unclear code,
even for the developer who originally made it after a while.    It is hard to understand and maintain, and it
becomes more and more complicated to reuse those objects in other code.



3.2.11 Too Many Fields
The Too Many Fields can be detected at the class level. It is a class with too many instance variables. "When
a class has too many instance variables, duplicated code cannot be far behind"[6, p. 65]


   It also shows the complexity of the maintenance of the code; each eld can be updated by each method in
the class and even in all the other classes of our system if the variable is made public. Impacts occur when we
want to modify those variables, we must be sure where and how they are updated.



3.2.12 Too Many Methods
The Too Many Methods can be detected at the class level. It is a class with too many methods. Each method
is supposed to add functionality to our class.


   Having too many functionalities can display a class gathering too many responsibilities. It means our design
could improved and could be decomposed. Unfortunately, it also means it takes more work to maintain and
evolve the code.

3.3 Identication of Code Smells
The Code Smells concept is a design aw in the Code. However, software engineering is not an exact science
with precise quality denitions. These quality denitions are concepts that need to be applied.


     The understanding of the smells can also depend on the knowledge of the developers themselves [14]. Santos
et   al [14] notes that even with a given denition of Code Smells, developers have trouble identifying them in the
Code. They also pointed out that developers will only consider a lousy design with symptoms as problematic
if they can not nd another way to implement it.


     Therefore, the denition of Code Smells and its categorization can vary from one study to another or from
one organization to another.

   On the other side, Lanza & Marinescu [10] dene a polymetric view to detect the possibility of bad smells
and code design. They select a set of metrics and their thresholds for each Code Smells and structural design

   All of those studies show us that it is complicated to identify a Code Smells. If detected with an automatic

might not even be considered a problem by developers [14, 15].



3.4 Prioritization & criticality of Code Smells
Charalampidou et     al [4] tried to assess the priority to give to the Code Smells through the concept of Interest
Probability that can be calculated by considering the number of occurrences of a Code Smells and the proba-
bility that developers will change its Code in the future.


   They worked on two open-source projects, and they found that:


    Code Clones are the most frequently found Smell, and at the same time, they are the least modied into
      a commit. Nevertheless, the fact that they are present in several methods means that they are counted
      several times and induce an interest probability of 4.5%-14% per commit.


    Long Method and Conditional Complexity are less frequently found in the methods but are more often
     updated into commits giving respectively 1.0%-2.0% and 0.5%-3.5% of interest probability.


They also note that Code Smells refactoring in commits is often hidden or mixed by developers with other
programming changes.
The study's limited scope cannot prove anything, but it lightens the fact that it is not because a Code Smells
exists that it is critical.


   On the other hand, Pecorelli et      al [13] tried to understand how developers categorize the criticality of Code
Smells and prioritize them. They led a survey for six months on open source projects, asking questions after
each commit to the developer who made it and to the rst developer who implemented the class. They also
observed which set of classes were modied in the same commit.


   They selected four Code Smells. The selection criteria were that they needed to be highly diused Code
Smells with high studied impacts on maintainability, comprehensibility, and Testability. They used an automatic

tool to detect those Code Smells in the selected projects . They identify the way developers determine criticality
is dierent for each Code Smells :


    Blob (God Class): the criticality is determined by structural factors, but those factors are linked together.
      One is not enough to dene criticality.


    Complex Class: it is also the structure of the Code (CBO,WMC, LCOM5) but with a relevant impact
      from readability too, showing us comprehensibility aect the prioritization.


    Spaghetti Code: no structural factors for the Spaghetti Code, it is Readability the key factor.

    Shotgun Surgery: the main factors are the process-related factors (the number of changes (NCh), the

   Those two studies show that even if a Code Smells is present or even frequent, it does not mean that it
will be critical. We can also understand that each Code Smells has its denition of criticality through multiple

4.2 Testability metrics
Testability can give valuable information during the whole development cycle of an application (design, coding,
testing, and quality insurance). However, there is no standard denition of metrics for assessing testability and
few studies in this area link testability to metrics.


   Furthermore, the testability is evaluated in some studies during in the software design phase [12, 17], others
in the development phase [3]. A comprehensive model could be the sh-bone model of Binder [2], which assesses
the testability through the whole life of the software.


   As we look at the impact of a wrong code design on testability, we will focus on the denitions in the

4.2.1 Fish-bone model - Testability through all the cycle

   With that in mind, he uses the concept dened by Freedman [7] that two key facets of Testability and
compliance exist: Controllability and Observability.
Controllability is the ability to control the input and internal states of the studied class. Observability is the
ability to check on the output.


   Besides those two "primal" factors, the author adds all the organizational and technical factors needed to
ensure Testability. He uses a dierent "bone" for each dimension with sub-dimensions to represent it. That

4.3 Testability eectiveness
In their study, Grano et    al. [8] decided to use mutation testing to draw a framework of metrics to assess the
Testability of a code. To be more precise, they try to evaluate the quality of the test suite.




4.3.1 Mutants
Mutants are created by mimicking faulty behaviour. Mutation testing is the idea of creating altered versions
of the source code to calculate a Mutation score. The calculation is made by running the mutants against the
test cases to see how many the test case kills.         It is the percentage of killed mutants over the total number
of mutants. The authors consider this technic as very powerful but expensive because it needs to create and
compile the mutant and go through all the test suits for each of them.
They want their empirical study to be able to directly assess the Mutation score of a production code by using
a set of dened code quality metrics.




4.3.2 Code metrics and Testability eectiveness
For the test of Code Smells, they selected 8 smells :


    Class Data Should Be Private

    Complex Class

    Blob

    Spaghetti Code

    Message Chain

    Long Method

    Feature Envy

    Functional Decomposition

   Of the eight tested Code Smells, only two have a signicant negative relationship with mutation score: Mes-
sage Chain and Feature Envy.
There is a small dierence in the readability. Grano et   al. [8] suppose that less readable Code makes it harder
to produce test code.


The authors concluded that cohesion, coupling, and complexity are the most important factors for test-case
eectiveness.


The most contributing metric is McCABE Cyclomatic Complexity, "a high complexity of production code in-
dicates the presence of several linearly independent paths "[8, p 12], which increases the diculty of having an
eective test.


   The second most important metric is Response For Class (RFC). Grano et         al. [8] remarks that the metric
shows the complexity in terms of methods and can lead some mutants not to be killed because, given the com-
plexity, some paths of the production code do not include a mutated instruction. We can conclude that this
metric does not work well with mutants.


   The same conclusion can be drawn for the Coupling-related Metrics Coupling Between Objects Classes
(CBO) and Message Passing Coupling (MPC). A high value in those metrics indicates several external invoca-
tions, which lead to several mutants not being killed.


   HALSTEAD Metrics present the same type of problem. It measures the complexity by computing the num-
ber of operands and operators. The test might not execute some operands; however, a mutant can be injected
into an operand meaning the test might not be able to kill it.


   The low contribution of Code Smells (only two on 8 had a signicant negative impact) into their model is
explained by the test method that can be "limited by the co-presence of other complexity metrics" [8, p 10].
   In other words, assessing the real impact of Code Smells on Testability is complicated, given their direct
link with some code metrics. Nevertheless, they could be the tree hidden in the forest.
   Their conclusion on the subject is that "the lower the number of code smells, the higher the ability of tests
to nd faults"[8, p 7]

7.3 Comparison with the Code Smells metrics
Our idea is to assess whether there is a relationship between each Code Smells and the two individual testability
metrics. We will rst start the reading with the Code Smells located on the class level. They have the advantage
of describing a boolean situation. It is present, or it is not.

Smells are present or not.

their presence in a class. It would undoubtedly be interesting to study the variations as a function of the number

more qualitative study, checking the lines of code and categorising the possible reasons for these variations and
the impact on testability.


   Since we know that our distributions are not normal, we need to use a non-parametric test to estimate the
probability that we are wrong in our reading of a signicant result. The test we will use is the Wilcoxon-Mann-
Whitney test.


   We will use this tests to check whether the medians of our two populations are equal. We are interested in
the case where this hypothesis of equality is not satised, the counter-hypothesis, where we observe a dierence
in Testability between the presence or absence of a Code Smells. The test gives us an indicator p. If its value
is less than 5%, we can reject the medians' equality hypothesis with reasonable certainty.

7.4 Challenging the results
These results should now be read with caution.     Inuencing Testability does not mean that this inuence is
direct.   An unknown factor could inuence both Testability and the Code Smells studied.       Our anti-pattern
would no longer be a cause, but a consequence of another factor, and the increase in eort to perform the test
would also result from this unknown factor.


   Given these limitations, it is interesting to note that almost all the Code Smells studied have an impact on
the Testability of the code.   We can see in our distributions a dierence, sometimes signicant, between the
number of unit tests and test cases and the presence or absence of certain Code Smells.


   The case of the Complex Class is the more interesting as there is a signicant dierence with the critical
complex class. This case highlights the importance of the 'Coupling Between Objects Classes' and 'Response
For Class' metrics.


   These two metrics refer to the behaviour linked to other classes, i.e. the number of external classes that
call the methods and attributes of our class and the number of methods accessed (internally and externally) by
the class. This could mean that it is more complicated to test behaviours linked to classes outside the class for
which the tests are being carried out.


   For the rest of our analysis, it would seem that the intuition that an anti-pattern creates an additional
diculty, a greater eort to test the code, has been conrmed.

Threats to validity
Both the Code Smells and Testability are qualitative measurements. Those measurements are estimated through
metrics. We used that estimation to estimate the relationship between our two concepts. Unfortunately, there
was a lot of guesswork to conrm of our result.


   To deepen that concern, we know that the Code Smells are not perfectly dened concepts. And even on the
more globally accepted and dened patterns, we saw that there are not always considered as an anti-pattern
given the situation.


   The thresholds are dierent for each metric depending on the language.          It shows us the complexity of
working with metrics and that they can also be relative to the person that denes them.


   Our calculation was not done by hand, nor by evaluating the classes one by one and checking if their concept
corresponded to a Code Smells. We also did not asked the developers for their opinion on the code. We only use
metrics to indicate the presence of anti-patterns. This use can create false positives or leave undetected patterns.


   The tools we used to assess the metrics could not calculate all of them. A good example is the LCOM5 that
requires calculating the number of   distinct attributes accessed by each method in a class. That is, right now,
not possible with the existing tools.


   Testability measures are also a compromise; we try to measure eort objectively. The best way to make
the measurement would be to ask one person to be sure that the knowledge does not inuence the score and
to do a test of all the projects. In reality, it is impossible; it would require a deep knowledge of many dierent
systems, logic and domains. That would require a long time to test enough projects, and we could argue that
that person would learn one thing or two in that long time, making him more eective on later projects than
on earlier ones.


   The choice of the projects has been a complicated decision. Choosing only the more qualitative projects
might show us projects with much less Code Smells.       However, on the other side, we might have better test
coverage, granting us good tests. We could imagine a less qualitative project with many Code Smells and not
all the needed test cases and asserts or the opposite with way too much tests.


   Some Code Smells were barely represented in our sample.         God Class, for example, was only present 38
times out of 9152 classes. This represents less than 0.4% of classes. The same can be said for Shotgun Surgery,
which was only present in 130 cases (1.42% of cases), and of course, for Critical God Class, which is an over-
interpretation of God Class.
                                                                    CHAPTER 8. THREATS TO VALIDITY

   It would be necessary to do a more extensive study to see if this low presence represents reality and if our
impact study on the distribution of testability measures repeats with more observations.


   We have also limited our analysis of Feature Envy and Shotgun Surgery patterns to whether or not they
are present in a class. Therefore, we cannot say whether their impact is directly linked to their number. As
explained earlier, it would require an in-depth study of the code to answer this question.


   Another limitation of our study is that we used metrics to detect Code Smells automatically.      We would
have to do a qualitative study with manual detection of Code Smells, according to clear denitions, to analyze
their possible impact on Testability. It may be that the links we have discovered are related more to indicators
than to concepts that are not initially dened by metrics but by other concepts.

Conclusion
This study assessed the relationship between Code Smells and Testability.


   We rst tried to understand the concept of Code Smells. We discovered that Fowler[6] has worked on the
concept since 1999, and we dened some of those anti-patterns.


   Nevertheless, we also discovered that there are not many studies on the subject and that the identication
of Code Smells is complex. These concepts can be interpreted dierently by each developer and organisation.


   Lanza & Marinescu[10] have worked on translating the Code Smells concepts into metrics allowing us to
detect them more easily. But it is still a concept; even if its characteristics are shown in a code, it does not
mean it exists.


   We then tried to understand whether there were more critical Code Smells and found that they were a more
restrictive denition of our concepts. We also found that it is not the most frequent Code Smells that are the
most critical or the highest priority for the developer. We can also add that whether illness of code are a Code
Smell depends on the context of the software. If it cannot be avoided, it is not considered a Code Smell by the
developers


   To conclude our study of the concept of Code Smells, we addressed the issue of detection tools that may
not use all related metrics to detect code smells. They also could have a lot of false positives in detection tools
given the domain of the observed system.


   We then dened our second concept: Testability.


   We saw that it was a dened quality of software by the ISO 25010[9] and that it conceptualises an eort
measurement.
We then tried to understand how to evaluate Testability. We have explained how Testability can be taken into
account in the dierent phases of the software life cycle. We then described the Testability metrics related to
the implementation phase.


   We also found that assessing Testability eectiveness using mutants can allow us to establish strong links
between Testability eectiveness and code metrics. However, Grano et       al.[8] did not nd a relationship between
the existence of Code Smells and the eectiveness of the corresponding tests. The only thing that the authors of
the study can conclude is "the lower the number of code smells, the higher the ability of tests to nd faults"[8, p 7]


   With both our concepts dened, we determined the scope of our analysis. Finally, we selected open-source
projects for our corpus. We picked the most relevant Code Smells to study and transformed them into metrics.
We added the metrics uncovered by Arcelli Fontana et         al [1] linked with the Code Smells. When possible,
we also added the metrics discovered by Pecorelli et     al [13] to create a critical class of Code Smells. We also
characterised the three metrics used to evaluate the Testability.


   Our next step was to determine how we would get the values for our metrics for all the selected projects.
We also dened all the processes that the measured data would go through to enable us to carry out our analysis.
                                                                                CHAPTER 9. CONCLUSION

   Our analysis does not allow us to say more that there is a signicant dierence in our samples when most
of the Code Smells observed are present. It exists an impact between some Code Smells and the Testability.
Unfortunately, we are not in a position to calculate the amplitude of this impact.


   As explained in the previous chapter, the fact that both parameters of our analysis are qualitative makes
it more complicated to assess. It creates another layer of complexity in the understanding of the possible rela-
tionship between Code Smells and Testability.


   We can ask whether Testability is not directly related to code metrics rather than Code Smells. The rela-
tionship between the two concepts may come from a few metrics that compose our denition of Code Smells. It
is what happened with the Complex Class and the Critical Complex Class. This means that we should perhaps
focus more on certain attributes of the code to improve Testability than on the existence of an anti-pattern.
That requires a complete study on the subject to nd if that relationship is more robust and what those related
metrics and their threshold would be.


   Our analysis shows the importance of studying the subject to better understand Code Smells and to provide
a more accurate and accepted denition. The same can be said about code metrics and their threshold. We
need to be able to better characterise code and its properties. But it should also be recognised that this would
be a complicated task given the speed of evolution of techniques and practices in our eld.
