 Résumé
    L'apprentissage de la programmation et surtout la compréhension de celle-ci sont une tâche dicile
pour les nouveaux arrivants. Pour cela, des aides sont prévues comme les Integrated Devlopment En-
vironment (IDE) qui leur fournissent des outils pour les aider à ne pas commettre d'erreurs de syntaxe
et/ou de sémantique selon les langages de programmation employés.

    Cependant, ces aides ne susent pas toujours à comprendre le code écrit et le plus souvent, ils
n'arrivent pas à comprendre les erreurs générées et leur cause. Pour cela, il existe des outils d'aide à
la compréhension de code qui permettent de visualiser le code. Certaines avancées ont même permis
d'utiliser cela à travers la réalité virtuelle.

    C'est pourquoi, avec l'arrivée de la réalité mixte (MR), une ébauche d'application de visualisation
de code a été proposée. Cette solution, codeMR, permet de représenter le code en 3 dimensions en
suivant le paradigme de la ville, codeCity. Pour en tester la viabilité, une expérimentation a été menées
sur 10 personnes pour voir si cela permettait d'entrevoir un avenir pour la compréhension du code à
travers la MR.

   Les résultats ont démontré que la solution possédait les capacités pour aider à la compréhension du
code. Cependant, des améliorations à l'application restent nécessaires pour en assurer une utilisation
optimale dans ce cadre.

Mots-clés : Compréhension de code, visualisation, virtualisation, codeCity, réalité mixte.




 Abstract
    Learning to program, and especially understanding it, is a dicult task for newcomers. For this rea-
son, aids are provided, such as IDEs, which give them tools to help them avoid syntax and/or semantic
errors, depending on the programming languages used. depending on the programming languages used.

    However, these aids are not always sucient to understand the written code, and more often than
not, they fail to to understand the errors generated and their causes. For this purpose, code compre-
hension tools are available to help visualize the code. Some advances have even made it possible to use
this through virtual reality.

    That's why, with the advent of MR, a draft code visualization application has been proposed. This
solution, called codeMR, makes it possible to represent code in 3 dimensions following the city's para-
digm, codeCity. To test its viability, an experiment was carried out with 10 people to see if it could a
future for understanding code through the mixed reality.

   The results showed that the solution had the capabilities to help code comprehension. However,
improvements to the application are still required to ensure optimal use in this context.

Keywords : code understanding, visualisation, virtualisation, codeCity, mixed reality.

1.1 Contexte
    La compréhension de code est un enjeu dans la programmation et cela, malgré l'émergence d'outils
automatisant la création de programme. Ces outils réduisent considérablement le temps de dévelop-
pement et permettent de réduire le nombre d'erreurs dans le code. On peut citer les outils d'aide à
la programmation inclus dans les environnements dédiés , les outils d'analyse statique de code, de

scaolding,. . .. Ils ont également permis à un plus grand nombre de personnes de se lancer dans la pro-
grammation sous le prétexte que la programmation, "c'est facile". Cependant, ils peuvent amener le
bon programmeur à faire d'autres types d'erreurs quand il programme surtout si le programme devient
de plus en plus complexe.

    Par programme complexe, on entend souvent un programme contenant énormément de chiers,
mais la dénition ne s'arrête pas là. En eet, un code source peut être complexe en raison de la di-
culté intrinsèque de l'algorithme qu'il implémente et de sa structure en elle-même, qui provoque une
diculté à le maintenir et à le faire évoluer dans le temps, ce qui peut alors demander énormément de
ressources cognitives aux développeurs amenant à un épuisement mental de ceux-ci.

    Cette charge cognitive peut provenir de diérentes sources comme le prol du développeur, sa ma-
nière de programmer ou encore l'environnement de développement en lui-même. En eet, le code en
tant que tel peut être réduit à un chier contenant un texte structuré d'une telle manière que l'on
sait déterminer avec quel type de langage il a été écrit. Ce contenu nous est alors présenté dans un
environnement sous la forme d'un arbre où chaque noeud est susceptible de contenir d'autres noeuds
en plus de chiers avec du code. Cette structure permet aisément de retrouver un chier donné si cet
arbre a du sens. Cependant, il n'aide pas à la compréhension globale du code. C'est-à-dire comment
le code peut fonctionner à l'exécution. De plus, cette structure en arbre peut vite devenir complexe à
comprendre au fur et à mesure que la profondeur de l'arbre augmente.

    Pour pallier ce problème, d'autres catégories d'outils ont été créées, ceux-ci mesurant la qualité
intrinsèque du code. On retrouve parmi eux la famille des linters. Ils se basent sur l'utilisation de
métriques permettant ainsi de réduire la dette technique [Fowler Martin, 2018]. Couplé aux outils

une trace du processus de qualité de notre code durant tout le cycle de vie de celui-ci, on dit alors du
code qu'il est vivant [Fowler Martin, 2018, Bourque Pierre, 2014]. Cela permet aussi une certaine au-
tomatisation de l'analyse du code, dont les résultats sont disponibles et accessibles à tous les membres
de l'équipe de manière quasi instantanée.

    On reste cependant sur une analyse statique du code et on n'échappe donc, pas à la représentation

ville. Chaque subdivision de la ville représente un quartier (package) et chaque bâtiment du quartier
une classe. À l'aide des outils précédemment cités et de leurs métriques récoltées, on peut paramétrer

2.1.1 La charge cognitive
    La charge cognitive est une théorie en psychologie qui s'intéresse à la capacité de retenir une infor-
mation et de pouvoir l'utiliser via notre mémoire de travail [Dalla Valle Maxime, 2020]. Cette théorie
essaie d'expliquer les situations d'échecs ou de réussites durant l'apprentissage des personnes en géné-
ral. En eet, la charge cognitive est la quantité d'informations que notre cerveau peut traiter en même
temps.

    D'ailleurs, toujours selon cette théorie, le cerveau humain peut en moyenne comprendre et traiter
seulement sept informations [Mason et Cooper, 2014]. En fonction de la personne, la moyenne peut
descendre à cinq et pour les plus expérimentés, elle peut monter à neuf. Dès lors, si on dépasse cette
limite, on peut se retrouver dans une situation de surcharge cognitive. Cela peut se traduire par une
incompréhension de l'information ou une incapacité à la retenir.

   On relève trois catégories de charge cognitive [Dalla Valle Maxime, 2020, André, 2014] :
    Charge intrinsèque : C'est la charge cognitive liée à la tâche à réaliser dans sa complexité.
    Charge extrinsèque ou externe : Charge cognitive relevant des facteurs externes comme la
       clarté de l'information, la qualité de l'enseignement . . ..
    Charge essentielle : C'est le niveau de concentration requis pour réaliser ou comprendre une
       tâche. Elle est liée à la charge intrinsèque et extrinsèque.
   En prenant en compte ces trois charges cognitives existantes, on peut ouvrir des pistes an d'assurer
une compréhension optimale de l'information de la part de l'individu. Elle inuencera le choix du
développement de l'application de réalité mixte.

2.2 La mémoire
   Il est bien connu qu'il faut d'abord apprendre à se connaitre pour optimiser notre compréhension
de quelque chose, la mémoire y joue alors le rôle principal quand il s'agit de retenir des éléments im-
portants.

    Pour un programmeur ou toute autre personne désirant retenir une quelconque information, il est
important de savoir le fonctionnement de notre cerveau lors du processus de mémorisation. trois "types
de mémoires" [Felienne, 2021] du cerveau sont impliquées dans ce processus de mémorisation :
     1. Mémoire à long terme : C'est la mémoire qui se charge de stocker les informations sur le
        long terme. On peut la comparer à nos disques durs.
     2. Mémoire à court terme : Elle permet le stockage de l'information à court terme. Elle permet
        de retenir une information de manière instantanée, mais sur une courte durée.
     3. Mémoire de travail ou zone de travail : Elle coordonne les informations pour générer des
        réponses données. Pour cela, elle fait appel aussi bien à la mémoire à court terme qu'à la mémoire
        à long terme.
    Ces trois mémoires fonctionnent en même temps et se coordonnent pour permettre une compréhen-
sion optimale d'une tâche quelconque. En analogie avec la programmation, le schéma conceptuel serait
le suivant : la mémoire à long terme stocke la syntaxe et les règles d'un langage, la mémoire à court
terme stocke les informations de la structure du code et la mémoire de travail coordonne, ensuite, les
deux pour en dégager le processus de réexion et atteindre la compréhension.

    Ce processus de traitement de l'information peut également faillir et entrainer une mécompréhen-
sion de l'information présentée. En eet, lors d'un apprentissage, plusieurs phénomènes peuvent en
eet être à l'origine de pourquoi on ne comprend pas celle-ci. On retrouve notamment le manque de
connaissance sur le sujet à traiter. On ne peut pas comprendre quelque chose si on ne connait pas
le sujet en question. Il existe aussi le manque d'accès à l'information. Il arrive également que l'on se
confronte en cours d'analyse à des éléments inconnus. Dès lors, il est important d'avoir accès à des
informations complémentaires pour amener le processus de compréhension à son terme. Le dernier
élément est le manque de motivation, ou de puissance cérébrale [Felienne, 2021]. Pour résumer, si on
n'est pas concentré un minimum sur le sujet, on ne peut pas comprendre correctement le thème abordé.

     Il existe également une autre forme de mémoire qui peut entrer en jeu lors de la mémorisation.
Elle s'appelle la mémoire épisodique [Sauzéon et al., 2012]. Elle est utile lors de l'enregistrement
d'événements de notre vie quotidienne. C'est elle qui nous rappelle les événements importants du passé.
Elle se charge de dénir des liens entre diérentes informations perçues par notre corps qu'elles soient
tactiles, visuelles ou encore auditives. Les émotions peuvent également inuencer la mémorisation de
l'information. En eet, si on ne ressent pas d'émotion particulière, on peut plus facilement oublier une
information. Dès lors, il est important de ressentir des sensations pour retenir une information.

    En prenant en compte ces diérents éléments, on peut alors facilement dire que le mélange de
diérentes informations sensorielles est indispensable pour une bonne mémorisation. On peut citer
l'exemple de l'expérience sur l'eet de la locomotion sur la mémoire [Sauzéon et al., 2012]. Elle cite
comme conclusion que les personnes bougeant durant l'apprentissage retiennent mieux l'information
que les personnes restant sédentaires.

    Une deuxième recherche d'expérience tend à démontrer les mêmes résultats sur l'importance de
la locomotion physique sur la mémorisation de l'information [Larrue et al., 2012]. Cette expérience
compare ici l'avantage de la locomotion physique par rapport à la locomotion en 100% virtuelle. Dès

3.3.8 Le mob programming
    Comme dit plus haut et déni dans l'état de l'art, l'application a pour but d'expérimenter et
d'entrevoir une incorporation du principe du mob programming dans un monde virtuel. Pour rappel,
celui-ci se veut comme un descendant de la méthode du pair programming et donc, des méthodes issues
de l'Agile et de l'XP, mais étendu à un plus large nombre de participants. Dans le cadre d'une future
possibilité, la méthodologie a été réduite à une utilisation par personnes en modiant légèrement la
procédure.

    Sachant cela, des rôles-clés sont à distinguer dans le mob programming (méthode de base) :
    1. Le scribe : Seule personne autorisée à écrire et à modier le code.
    2. Le navigateur : Rôle le plus important. Il se charge de guider le scribe et retranscrit l'avis du
       public et le sien au scribe.
    3. L'équipe : C'est elle qui guidera les choix de modication et de réécriture du code. Elle donne
       son avis au navigateur qui le retranscit au scribe.
    En toute généralité, le mob programming a comme objectif de partager une visualisation de code
commune à un ensemble de personne. La majorité des personnes deviennent l'équipe. Elles sont guidées
dans leur choix par le navigateur/guide qui s'occupe de regarder le code vers de possibles endroits où
pourraient se trouver de potentiels code-smells. L'équipe suggère alors des modications. Après cela,
le navigateur synthétise l'avis de l'équipe pour ensuite, avertir le scribe qui modiera le code en consé-
quence.

   La mise en application du principe sera décrite dans une prochaine section de ce mémoire.

     Pour résumer, codeMR repose sur l'architecture client-serveur. Le composant central étant
     l'API SC. Nous avons alors deux composants qui travaillent en communiquant directement
   avec elle. Le premier, la code base, est mis sur un répertoire en ligne sur github. Github, grâce

6 Conclusion
    Les technologies de monde virtuel sont devenues accessibles à un plus grand nombre de personnes
ces dernières années. Il est normal que de nombreux secteurs dont celui de l'informatique s'y intéressent
dorénavant davantage. Comme dans tout métier, il est important d'en connaitre les bases pour en ef-
fectuer les tâches et l'informatique n'y déroge pas avec l'apprentissage des bases de la programmation.
C'est pourquoi une bonne compréhension du code que l'on écrit est primordiale. Cependant, elle peut
s'avérer ardue au début. Et cela est d'autant plus vrai pour des apprenants novices en informatique.

    L'inuence et la théorie de la charge cognitive est intimement liée à la facilité d'apprentissage. Cette
théorie tend à prouver que plus on éprouve de dicultés dans l'apprentissage, plus la charge cognitive
est élevée. Celle-ci se résume par l'eort mental à fournir dans la réalisation d'une tâche quelconque.
Pour la diminuer, on peut adapter l'apprentissage aux apprenants en prenant en compte son prol, sa
manière d'apprendre,. . .

   La solution apportée par le biais de ce travail est un prototype d'application de réalité mixte,
codeMR, axé sur la visualisation de code et la MR. L'application a pour but ici de savoir si la visua-
lisation du code peut aider à la compréhension d'une 'code base' et de faciliter l'apprentissage de la
compréhension du code et par extension de la programmation en général, mais également en essayant
d'appliquer la méthode de programmation appelée "mob programming".

    L'utilisateur de l'application peut ainsi voir à travers son casque une ville représentant une "'code
base'". Cette représentation du code mappé en ville porte le nom de codeCity. Celle-ci est découpée
en quartiers représentant des classes. Chaque classe est représentée par un immeuble. Des infomations
utiles sont achées par le biais de 2 popups se déclenchant quand une certaine distance entre l'utilisa-
teur et le bâtiment en question est respectée. Ces informations sont le code de la classe en question et
les métriques de celle-ci. En achant ces informations, l'application ore la possibilité à l'utilisateur
de voir le code et de l'évaluer. De plus, grâce à l'expérience et aux réponse du troisième questionnaire,
on peut entrevoir positivement l'application de la méthode du "mob programming" dans une version
future de l'application.

   L'usager a donc à sa disposition une application originale et stimulante pour l'aider dans la com-
préhension du code qu'il écrit. Cependant, étant donné le prototypage de l'application, il est important
de continuer à l'améliorer pour qu'elle soit plus ecace et plus adaptée à l'apprentissage de la pro-
grammation et à la méthode du "mob programming". Les points à améliorer sont l'attractivité, la
compréhensibilité, l'ecacité et la contrôlabilité. Une fois ces aspects corrigés, on aura une application
qui devrait satisfaire les besoins des utilisateurs et donc, diminuer de manière plus signicative sa
charge mentale.

    7.4 Annexe 4 : note du projet
    1 L'api sonarcloud
        L'architecture globale de l'application repose sur une architecture client serveur. Celle-ci se ca-
    ractérise par une machine cliente (ordinateur, téléphone,. . .) interrogeant un serveur distant chargé
    d'eectuer des calculs et de répondre à la demande de la requête.

    1.1 Description
       Cette partie se concentre sur la description de diérents points requiérant une attention particulière.
    On parlera notamment de la structure des requétes Http, mais aussi de l'algorithme de damier.

    1.1.1 Les requêtes Http
        La première étape consiste à créer un objet de type HttpClient. C'est une classe se trouvant dans la
    librairie System.Net.Htpp. Elle permet de créer des requêtes http. Pour commencer, on instacie dans
    ce cas-ci l'objet à vide grâce au constructeur de la classe. Ensuite, on utilise la propriété, méthode
    .BaseAdress pour spécier l'adresse de point d'entrée du serveur en prenant sooin de lui aecter
    l'adresse sous la forme d'un objet de type Uri.
        De plus, l'api SC requiert une clé d'authentication (token) pour l'accès à ses services. Elle sert
    également de preuve que la machine client a bien le droit d'accéder à telle ressource. Ce token est
