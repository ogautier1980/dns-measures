\chapter{Method}
\label{ch:method}

\section{Overview}
\label{sec:3.1}

\subsection{Methodological Objective}
\label{subsec:3.1.1}

The global methodological objective of this thesis is to capture the geographic and temporal diversity of \ac{DNS} responses for a representative corpus of popular domains, using geographically distributed active measurements, in a manner that is reproducible, ethically sound, and practically feasible within the available resource budget. The system must answer four empirical research questions:

\begin{itemize}
  \item \textbf{Q1}: What proportion of Tranco top-ranked domains return geographically differentiated \ac{DNS} responses, and what infrastructure mechanisms explain the differentiation?
  \item \textbf{Q2}: What is the temporal stability of \ac{DNS} responses for popular domains at day, week, and month timescales?
  \item \textbf{Q3}: Do the geographic biases of the RIPE Atlas probe distribution significantly limit the ability to observe geographic \ac{DNS} variation?
  \item \textbf{Q4}: Do the three major public \ac{DNS} resolvers return consistent \ac{DNS} responses for the same domain queried from the same geographic location, and how large is the divergence?
\end{itemize}

\subsection{System Architecture}
\label{subsec:3.1.2}

The measurement system is organised in five sequential stages, inspired by the architecture of OpenINTEL \cite{vanRijswijk2016} but adapted to the constraints and capabilities of the RIPE Atlas platform:

\begin{enumerate}
  \item \textbf{Domain corpus preparation}: Retrieval and filtering of the Tranco Top 250 domain list.
  \item \textbf{Measurement scheduling}: Configuration and deployment of RIPE Atlas \ac{DNS} measurement campaigns.
  \item \textbf{Data collection}: Automated daily retrieval of measurement results via the RIPE Atlas REST API.
  \item \textbf{Storage and preprocessing}: Parsing, validation, and archival in Parquet format.
  \item \textbf{Analysis}: Quantitative analysis addressing Q1--Q4.
\end{enumerate}

Every design decision in this system involves a credit budget constraint: measuring more domains, using more probes, or increasing measurement frequency each raises the daily cost. The system exposes \texttt{--max-domains} and \texttt{--total-probes} to adjust these parameters independently. The first main campaign ran at 250 domains and 200 probes, consuming approximately 500,000 credits per day (250 $\times$ 200 $\times$ 10 credits per measurement).

\subsection{Infrastructure}
\label{subsec:3.1.3}

To ensure continuous and autonomous operation throughout the 127-day campaign, the entire pipeline is deployed within a Docker container on a Raspberry Pi 5 (ARM64 architecture). This low-cost, always-on hardware setup eliminates the need for manual intervention during long-term data collection.

Built upon the \texttt{python:3.11-slim-bookworm} base image, the container is compiled natively for ARM64 to guarantee optimal hardware compatibility. Minimizing resource overhead was a priority; by limiting dependencies strictly to core libraries - including dnspython, pandas, pyarrow, scipy, matplotlib, and rclone - the final image footprint remains comfortably under 1 GB.

For data persistence, Docker named volumes safeguard metrics against container restarts or image deployments. Finally, automated remote backups are executed daily via rclone, which securely synchronizes the accumulated results to a dedicated Google Drive repository.

The pipeline is orchestrated by a cron daemon running inside the container, with the following schedule (all times UTC):

\begin{table}[H]
\centering
\small
\begin{tabular}{l l l}
\toprule
\textbf{Time (UTC)} & \textbf{Day} & \textbf{Action} \\
\midrule
10:00 & Daily & Fetch RIPE Atlas results + Parquet parsing \\
11:00 & Daily & Cloud sync (Parquet + raw JSON $\rightarrow$ Google Drive) \\
12:00 & Sunday & Q1--Q4 analysis + figure generation \\
13:00 & Sunday & Cloud sync (reports + figures $\rightarrow$ Google Drive) \\

\bottomrule
\end{tabular}
\end{table}

The weekly Tranco list refresh is intentionally disabled during the active measurement period. Keeping the domain corpus fixed throughout the campaign is required for the validity of the Q2 temporal stability analysis: if domains entered or left the measurement set mid-campaign, observed response changes could not be distinguished from corpus changes. The corpus will be refreshed after the measurement period concludes.

The pipeline source code is available at \url{https://github.com/ogautier-unam/dns-measurements}. The five core scripts (\texttt{fetch\_tranco.py}, \texttt{create\_ripe\_measurements.py}, \texttt{fetch\_ripe\_atlas.py}, \texttt{parse\_dns\_results.py} and \texttt{analyse\_dns.py}) are introduced as they appear in the pipeline, alongside \texttt{pipeline.py}, which acts as the top-level orchestrator and is invoked by the cron scheduler.

\section{Domain Corpus Selection}
\label{sec:3.2}

\subsection{Tranco List Configuration}
\label{subsec:3.2.1}

The domain corpus is the Tranco Top 250 list, retrieved via the Tranco API at \url{https://tranco-list.eu}. The choice of Tranco over commercial ranking lists (Alexa — discontinued May 2022 —, Cisco Umbrella, Majestic) is motivated in Chapter 2 (Section~\ref{sec:2.6}) and rests on three properties established by Le Pochat~\cite{LePochat2019}: stability (0.6\% daily change versus approximately 50\% for post-2018 Alexa), manipulation resistance (quadrupled manipulation effort relative to single-source lists), and archivability (each generated list is assigned a unique identifier retrievable indefinitely via permalink).

To compile the domain corpus, the \texttt{fetch\_tranco.py} script downloads the latest ranking dataset, with a built-in seven-day fallback mechanism in case the current day's list is delayed. Crucially, this selection happens exclusively at the launch of each campaign; the corpus remains strictly frozen thereafter. While Tranco provides highly stable rankings, introducing any mid-campaign modifications to the domain set would inject a confounding variable. Specifically, domain rotation would conflate actual \ac{DNS} response variations with shifts in the corpus itself, obscuring the true temporal instability we aim to evaluate in Q2. To guarantee full reproducibility, the exact Tranco list identifier, generation date, and retrieval timestamp are archived in \texttt{tranco\_meta.json}.

\subsection{Domain Corpus Size}
\label{subsec:3.2.2}

The empirical data collection was split into two sequential phases, tailored to the constraints of our RIPE Atlas credit allocations:

\textbf{The Pilot Phase (2--10 April 2026)}: To verify the end-to-end pipeline before committing significant resources, we restricted this initial run to the top 100 domains across 50 probes. Operating at this scale drew roughly 50,000 credits daily, allowing us to thoroughly test probe selection, measurement initialization, daily retrieval, parsing, and cloud synchronization without exhausting our budget.

\textbf{First Main Campaign (11 April -- 11 June 2026)}: Once the infrastructure was validated, with approximately 50,000,000 RIPE Atlas credits available, the scope expanded to 250 domains and 200 probes. Two domains that failed \ac{NS} pre-resolution were excluded, yielding 248 active measurements. This configuration consumed approximately 500,000 credits per day over 62 days, totalling approximately 31,000,000 credits. Probe selection for this campaign relied on RIPE Atlas geographic zone-based distribution.

\textbf{Second Main Campaign (14 June -- 8 August 2026)}: After a two-day interruption (12--13 June) to renew measurements, a second campaign ran for 56 days with 201 active domains and 150 probes, implementing the continent-level stratification algorithm described in Section~\ref{subsec:3.3.1}. This improved probe selection achieved coverage of 136 countries via a fixed probe set, with 201 domains returning daily results.

The choice of 250 domains for the first campaign reflects a trade-off between two competing constraints:

\textbf{Representativeness}: The Tranco Top 250 covers the most traffic-intensive domains, where \ac{CDN}-backed geographic routing is most prevalent. Studies by Calder~\cite{Calder2015} and Wang~\cite{Wang2018} confirm that \ac{CDN} routing diversity is most pronounced in the highest-traffic domains, but measurable geographic variation extends into the broader popular-domain tier, motivating the extension beyond the pilot corpus.

\textbf{Feasibility}: Deploying 200 probes across 250 domains results in a daily consumption of approximately 500,000 credits, within the available budget of approximately 50,000,000 credits (allocated credits supplemented by credits continuously earned from hosting one RIPE Atlas probe).

For the second campaign, new concurrent measurement limits imposed by the RIPE Atlas platform between the two campaigns reduced the probe count from 200 to 150 and the active domain corpus from 250 to 201. This configuration consumed approximately 300,000 credits per day.

The pipeline exposes \texttt{--max-domains} and \texttt{--total-probes} parameters, so the corpus can be extended to a larger Tranco slice without any further modification.

\subsection{Domain Filtering and Validation}
\label{subsec:3.2.3}

Before the measurement campaign begins, each domain in the Tranco list is pre-validated by 

\texttt{fetch\_tranco.py} in two steps:

\textbf{Technical validity}: A \ac{DNS} \ac{A} record query is issued against Google Public \ac{DNS} (8.8.8.8) and Cloudflare \ac{DNS} (1.1.1.1) as reference resolvers. Domains returning \texttt{NXDOMAIN} or \texttt{SERVFAIL} are excluded. Applied to the Tranco Top 10,000 list from which the campaign corpus is drawn, this step yielded 8,365 valid domains --- a filtering rate of approximately 16\%, higher than the 5--6\% reported by Le Pochat~\cite{LePochat2019}, which may reflect the broader scope of the list and the inclusion of parked or inactive domains in lower-ranked positions.

\textbf{Authoritative server pre-resolution}: To identify the authoritative name servers for each target domain, the system resolves their corresponding \ac{NS} records using the same reference resolvers. This initial step maps every domain to its respective authoritative server set, producing a compiled dataset archived as \texttt{tranco\_corpus.csv} with three core fields: \texttt{rank}, \texttt{domain}, and \texttt{ns} (the latter stored as a pipe-separated list of server hostnames). Any domains whose \ac{NS} \ac{IP} addresses fail to resolve at the exact time of measurement are automatically omitted from the campaign. During the first campaign, two domains were excluded under this criterion, yielding 248 active measurements. The same validation is applied at the start of each subsequent campaign.

\section{RIPE Atlas Measurement Configuration}
\label{sec:3.3}

\subsection{Probe Selection}
\label{subsec:3.3.1}

Probe selection is implemented in \texttt{create\_ripe\_measurements.py} and follows the filtering protocol recommended by Bajpai~\cite{Bajpai2017}. Geographic distribution across zones is delegated to RIPE Atlas. The selection proceeds in three steps.

\textbf{Step 1 --- System tag filtering}: All probes must satisfy the following RIPE Atlas system tags:

\begin{itemize}
  \item \texttt{system-ipv4-works}: \ac{IPv4} connectivity verified by built-in platform measurements.
  \item \texttt{system-resolves-a-correctly}: The probe's local resolver returns correct \ac{A} records, filtering out probes whose resolver intercepts or misroutes external queries~\cite{Boswell2024}.

\end{itemize}

Hardware probe selection is restricted to version v3 and newer to mitigate performance bottlenecks. As documented by Holterbach~\cite{Holterbach2015}, concurrent tracking workloads introduce significant timing anomalies in v1 and v2 hardware, distorting results by up to +7.7 ms at the 95th percentile. Upgrading to v3 hardware effectively resolves this issue, restricting degradation to a baseline of +0.06 ms. It is worth noting that software-based probes operate independently of these specific hardware processing limitations.

\textbf{Step 2 --- Geographic distribution}: Two approaches were used across the two main campaigns.

\textbf{First main campaign (200 probes)}: Geographic distribution was delegated to RIPE Atlas using five built-in geographic zones, which independently assign probe sets per measurement:

This inverse weighting reduces Europe's share from 40\% to 9.3\% and North America's from 28\% to 11.3\%, in favour of Asia-Pacific (16\% $\rightarrow$ 38\%) and Africa (5\% $\rightarrow$ 26\%), directly counteracting the structural bias of the RIPE Atlas probe network. The probe count is configurable via \texttt{--total-probes}.

\textbf{Step 3 --- Country and \ac{AS} diversity}: To maximize both sovereign country representation and \ac{AS} diversity, the pipeline executes a three-stage selection algorithm within each continental stratum:

\begin{itemize}
  \item \textbf{Phase 1 (Geographic Baseline)}: The system allocates one probe per nation, purposefully giving priority to countries that are not geopolitiquement or structurally integrated into a larger neighbour's network. During this initial pass, European micro-states and dependencies—such as Luxembourg, Monaco, or Gibraltar—are intentionally de-prioritized. This choice stems from the fact that their local \ac{DNS} infrastructure usually resolves through the exact same \ac{CDN} \ac{PoPs} as their dominant neighbours.
  \item \textbf{Phase 2 (Quota Management)}: If the overall continental probe quota remains unfilled after the first pass, the algorithm introduces one probe per previously de-prioritized micro-state or territory.
  \item \textbf{Phase 3 (\ac{AS} Broadening)}: Finally, any remaining slots within the quota are populated by adding extra probes to already-selected countries. In this round, the pipeline explicitly prioritizes unique \ac{AS}s to guarantee architectural diversity.
\end{itemize}

Within each round, the probe selected for a given country is the one with the highest hardware version that introduces a new \ac{AS} not yet represented in the selected set. The selected probe set is saved as \texttt{selected\_probes\_<date>.json} for full reproducibility. This algorithm was activated for the second campaign (14 June -- 8 August 2026, 150 probes), replacing the zone-based assignment used in the first campaign.

\subsection{Primary Campaign: Direct Authoritative DNS Queries}
\label{subsec:3.3.2}

The primary measurement campaign queries authoritative name servers directly, bypassing recursive resolvers. As discussed in Chapter 2 (Section~\ref{sec:2.5}), two complementary approaches are possible: using the probe's default resolver (which reflects real user experience) or querying the authoritative server directly (which isolates the geographic routing signal). For Q1--Q3, the direct authoritative approach is chosen for two reasons:

\begin{enumerate}
  \item \textbf{Resolver centralization} \cite{Xu2023}: Over 90\% of forwarding resolvers are backed by fewer than 5\% of indirect recursive resolvers. Querying through probe resolvers would collapse the geographic diversity of probe vantage points into a small number of centralised resolution paths, making geographic \ac{DNS} variation invisible.
  \item \textbf{Cache state divergence}: When probes rely on local resolvers, their heterogeneous cache states can introduce artificial variations. These discrepancies often mimic genuine geographic routing differences, whereas they are merely artifacts of cache timing synchronization. Conducting direct queries to authoritative name servers completely eliminates these caching anomalies from the measurement data.
\end{enumerate}

For Q4 (Section~\ref{subsec:3.3.3}), three major public resolvers are targeted explicitly, in order to isolate resolver-induced differences in returned \ac{IP} addresses.

For each domain in the corpus, the primary authoritative name server identified during pre-resolution is used as the measurement target. The RIPE Atlas \ac{DNS} measurement is configured as follows:

\section{Data Collection and Processing}
\label{sec:3.4}

\subsection{Daily Collection Pipeline}
\label{subsec:3.4.1}

Measurement results are collected from the RIPE Atlas REST API by \texttt{fetch\_ripe\_atlas.py} on a daily schedule at 10:00 UTC, retrieving results for the previous calendar day. The script reads the measurement plan from \texttt{measurements.json} (produced by \texttt{create\_ripe\_measurements.py}) and iterates over all active measurement identifiers.

The collection is fully paginated, following RIPE Atlas API \texttt{next} links until all results for the time window are retrieved. Error handling includes automatic retry with exponential back-off (up to 5 attempts, base delay 2 seconds, doubling on each retry) and explicit handling of \ac{HTTP} 429 rate-limit responses (waits for the \texttt{Retry-After} header duration before retrying). Should any measurement IDs fail after all retries, they are recorded in \texttt{fetch\_errors\_<date>.json} for subsequent investigation; no such file was produced over the 127-day campaign. Already-retrieved files are skipped unless \texttt{--force} is specified.

The raw results are stored in JSON files, which are kept in the data/raw/ folder and named \texttt{data/raw/m\-sm\_<id>\_<date>.json}.

\label{subsec:3.4.2}

The \ac{NSID} value is extracted by decoding the raw ABUF binary field: the script walks the \ac{DNS} packet structure to locate the OPT record (type 41) in the Additional section, then parses EDNS0 options to extract option code 3 (\ac{NSID}, ~\cite{RFC5001}).

\subsection{Data Validation}
\label{subsec:3.4.3}

The following validation filters are applied during parsing:

\textbf{RCODE filtering}: Only results with \texttt{rcode = 0} (NOERROR) and \texttt{answer\_count > 0} are used for Q1 and Q2 content analysis. Results with \texttt{rcode != 0} are retained in the Parquet dataset with their specific error codes for reliability and censorship analysis.

\textbf{Deduplication}: To prevent data inflation during the daily append process, the cumulative Parquet file (\texttt{dns\_results.parquet}) undergoes a strict deduplication pass based on the composite key \texttt{(msm\_id, prb\_id, timestamp)}. Crucially, the \texttt{timestamp} field records the exact moment the probe executed the \ac{DNS} query rather than the subsequent script retrieval time. Consequently, re-fetching data from an overlapping period generates identical tuples, allowing the deduplication logic to reliably isolate and discard any redundant entries.

\subsection{Storage Architecture}
\label{subsec:3.4.4}

Results are stored in a single-tier Parquet architecture optimised for the analytical query patterns of the analysis phase:

\textbf{Cumulative Parquet file} (\texttt{data/processed/dns\_results.parquet}): All parsed results are appended daily to a single Parquet file using pyarrow with a fixed schema. Over the full 127-day campaign, this file reached 113 MB (approximately 27 MB/month on average, with higher growth during the first campaign at 200 probes and lower during the second at 150 probes), thanks to columnar compression with dictionary encoding for repeated string values such as \texttt{country\_code}, \texttt{continent}, and \texttt{answer\_ips}.

\textbf{Daily archives} (\texttt{data/processed/dns\_results\_<date>.parquet}): In addition, the system preserves individual daily Parquet files. This redundancy serves a dual purpose: it facilitates granular, point-in-time analyses and provides a reliable rollback mechanism should the cumulative file suffer from data corruption.

\textbf{Raw JSON files} (\texttt{data/raw/msm\_<id>\_<date>.json}): The pipeline enforces a 7-day retention policy for raw RIPE Atlas JSON payloads, purging them locally once cloud synchronization is complete. This temporary buffering strategy provides a safety margin to re-parse raw data with updated schemas if necessary, while simultaneously keeping local disk space consumption within the strict limits of the Raspberry Pi.

\textbf{Cloud backup}: Every 24 hours, the pipeline invokes rclone to push all Parquet datasets, historical archives, and reports to a remote Google Drive repository. To ensure operational continuity, the underlying configuration metadata is maintained inside a dedicated Docker named volume, rendering it immune to container updates or service restarts.

\section{Analysis Methods}
\label{sec:3.5}

This section describes the analytical methods implemented in \texttt{analyse\_dns.py} (step 5 of Table~\ref{tab:pipeline_stages}). The script reads the cumulative \texttt{dns\_results.parquet} file and produces, for each research question, a CSV report and one or more PNG figures.

\subsection{Statistical Testing Approach}
\label{subsec:3.5.1}

Several analyses in this section compare two independent groups of observations (e.g.\ probes from different geographic regions, or different resolver types). All such comparisons use the Mann-Whitney U test (also known as the Wilcoxon rank-sum test), a non-parametric test that evaluates whether one group tends to produce systematically larger values than the other, without assuming any particular distribution of the data.

The Mann-Whitney U test was chosen instead of a Student's t-test. The t-test is a parametric test that compares the means of two groups under the assumption that the data follow a normal distribution; it is widely used but sensitive to violations of that assumption. Here, two characteristics of the data make the t-test unsuitable. First, the primary response variable --- the number of unique \ac{IP} addresses observed per domain --- is a count variable with a heavily right-skewed distribution: most domains return one or two \ac{IP} addresses, while a small number of \ac{CDN}-heavy domains return many more, violating the normality assumption. Second, the groups being compared are of unequal size, which further reduces the reliability of parametric tests on small samples. The Mann-Whitney U test is robust to both non-normality and unequal group sizes.

Under this framework, each statistical comparison tests the null hypothesis that both groups originate from an identical underlying distribution, implying the absence of any systematic divergence. We enforce a strict significance threshold throughout, rejecting the null hypothesis only when the resulting p-value falls below 0.05.

\subsection{Q1 --- Geographic Diversity of DNS Responses}
\label{subsec:3.5.2}

\textbf{Objective}: To assess every domain within the corpus in order to detect whether the returned sets of \ac{IP} addresses exhibit systematic variations correlated with the geographic location of the querying probe.

The analysis operates at two spatial granularities --- continental and national --- leveraging the country-level coverage enabled by the stratified probe selection algorithm (Section~\ref{subsec:3.3.1}).

\textbf{Step 1: Coarse-Grained Continental Diversity}. The initial analytical layer partitions the active probe infrastructure by continent for every individual domain and measurement campaign. By computing the total union of all returned \ac{IP} addresses within each continent, the system flags a domain as continent-diverse if at least two distinct continents record non-overlapping \ac{IP} pools on the identical day. This baseline alignment facilitates a direct comparison with traditional RIPE Atlas \ac{DNS} methodologies.

\textbf{Step 2: Fine-Grained National Differentiation}. The pipeline subsequently replicates this aggregation logic at the country level. A domain achieves a country-diverse classification if two or more nations yield divergent \ac{IP} address responses within the same 24-hour window. Refining the granularity to this scale exposes critical intra-continental routing discrepancies — such as localized variations within the European network fabric or distinct pathing splits between Brazil and Argentina — that remain completely hidden during continent-level evaluation.

\textbf{Step 3: Longitudinal Aggregation}. To evaluate the persistence of these routing behaviours over the entire 127-day campaign, we calculate the metric \texttt{pct\_geo\_diverse}, representing the exact proportion of observation days exhibiting geographic differentiation. A domain satisfies our broader geographic diversity criterion provided it triggers this differentiation signature on at least one operational day.

\textbf{Step 4: \ac{NSID} Structural Disambiguation}. For domains demonstrating geographic \ac{IP} variation, the framework evaluates \ac{NSID} payloads to isolate the underlying routing mechanism. This heuristic successfully separates Anycast instance selection (characterized by distinct \ac{NSID} responses across regions, indicating localized Anycast \ac{PoP} termination) from \ac{DNS}-driven \ac{CDN} routing, where identical \ac{NSID} strings pair with dynamic \ac{A} records, pointing to a central geographic database lookup.

\textbf{Key metrics}:
\begin{itemize}
  \item Proportion of domains exhibiting continent-level geographic diversity
  \item Proportion of domains exhibiting country-level geographic diversity
  \item Proportion of domains exhibiting intra-continental diversity (country-level only)
  \item Distribution of the number of distinct \ac{IP} address sets across countries and continents
  \item Top domains by country-level geographic diversity score
  \item Proportion of geographically diverse domains returning \ac{NSID} values
\end{itemize}

\subsection{Q2 --- Temporal Stability}
\label{subsec:3.5.3}

\textbf{Objective}: Quantify the rate of change of \ac{DNS} responses for each domain over time.

\textbf{Step 1 --- Per-probe change detection}: For each (domain, probe) pair, consecutive daily observations are compared. A change event is recorded when the \texttt{answer\_ips} value differs between two consecutive measurement days.

\textbf{Step 2 --- Change Frequency Quantification}: Based on these localized transitions, the system computes an aggregate change rate for each domain, defined as the proportion of observation windows where at least one probe records a shift in the \ac{IP} address set. To capture different operational dynamics, this metric is evaluated across three distinct temporal scales: daily intervals (consecutive tracking days), weekly spans (observations spaced 7 days apart), and monthly cycles (observations separated by a 30-day window).

\textbf{Step 3 --- Corpus-Wide Stratification}: The final analytical layer evaluates the statistical distribution of these change rates across the entire domain dataset. This step categorizes the corpus into distinct behavioural cohorts, pinpointing the exact proportions of fully static, occasionally shifting, and highly volatile domains.

\textbf{Key metrics}:
\begin{itemize}
  \item Distribution of per-domain daily change rates
  \item Proportion of fully stable domains (0\% change rate)
  \item Median change rate across the corpus
  \item Stability breakdown by temporal window (day/week/month)
\end{itemize}

\subsection{Q3 --- Assessment of RIPE Atlas Geographic Bias}
\label{subsec:3.5.4}

\textbf{Objective}: Quantify how much the disproportionate concentration of RIPE Atlas probes within Europe and North America skews or restricts our visibility into geographic \ac{DNS} variations.

To evaluate this potential infrastructure bias, the analysis mirrors the dual-layered granularity established in Q1, examining the dataset at both the continental and national scales. Each of these structural sub-analyses relies on the non-parametric Mann-Whitney U test detailed in Section~\ref{subsec:3.5.1} to ensure robust, distribution-free comparisons.

\textbf{Continent-level bias}: The probe distribution actually achieved at deployment is compared to the target allocation from Section~\ref{subsec:3.3.1}. For each continent, the coverage rate (proportion of domains observed by at least one probe) and the mean number of unique \ac{IP} addresses observed per domain are computed. The Mann-Whitney U test compares the distribution of unique \ac{IP}s per domain between Europe+North America probes and probes from all other regions. A statistically significant result indicates that the geographic stratification captures meaningfully different \ac{DNS} responses from under-represented regions; a non-significant result would suggest that EU+NA probes alone would have been sufficient.

\textbf{Country-level bias}: The combined dataset aggregates probe contributions per country across both campaigns and all 127 measurement days. This produces two analytical cohorts: countries from which only a single unique probe contributed data throughout the entire campaign (peripheral nations at the limits of RIPE Atlas coverage), and countries covered by multiple distinct probes. The Mann-Whitney U test evaluates the count of unique \ac{IP} addresses observed per domain, contrasting these two cohorts. A statistically significant outcome demonstrates that peripherally covered countries capture genuinely distinct \ac{DNS} behaviours, justifying the investment in broad geographic coverage. A non-significant result would imply that expanding national coverage yields administrative breadth without additional observational value.

\textbf{Key metrics}:
\begin{itemize}
  \item Actual probe distribution by continent and by country at deployment
  \item Number of distinct countries with at least one probe
  \item Number of single-probe vs.\ multi-probe countries per continent
  \item Mean unique \ac{IP}s per domain per continent
  \item Mann-Whitney U: EU+NA vs.\ other continents
  \item Mann-Whitney U: single-probe vs.\ multi-probe countries
\end{itemize}

\subsection{Q4 --- Impact of Resolver Choice}
\label{subsec:3.5.5}

\textbf{Objective}: Quantify how much the selection of a public \ac{DNS} resolver alters the \ac{DNS} responses observed from the same geographic vantage points, comparing Google (8.8.8.8), Cloudflare (1.1.1.1), and Quad9 (9.9.9.9).

This assessment leverages the dedicated Q4 measurement campaign detailed in Section~\ref{subsec:3.3.3}, which yields a matrix of three concurrent resolver observations across 250 domains and 200 probes.

\textbf{Step 1 — Baseline Resolver Profiling}. The pipeline extracts aggregate performance profiles for each resolver (\texttt{google}, \texttt{cloudflare}, \texttt{quad9}). For each resolver, we compute the error rate (proportion of non-zero RCODE outputs), the mean and median \ac{RTT}, and the mean number of returned answer records.

\textbf{Step 2 — Pairwise \ac{IP} Divergence}. At the individual (domain, probe) level, the system compares the \texttt{answer\_ips} pools returned by each pair of resolvers. A divergence event is recorded when the \ac{IP} sets differ between two resolvers for the same (domain, probe) pair. The divergence rate is the fraction of successful query pairs exhibiting this discrepancy, computed for each of the three resolver pairs (CF/G, CF/Q9, G/Q9).

\textbf{Key metrics}:
\begin{itemize}
  \item Error rate, mean \ac{RTT}, and median \ac{RTT} per resolver
  \item Mean answer record count per resolver
  \item Pairwise \ac{IP} divergence rate: Cloudflare vs.\ Google, Cloudflare vs.\ Quad9, Google vs.\ Quad9
\end{itemize}

\section{Ethical Considerations and Reproducibility}
\label{sec:3.6}

\subsection{Ethical Design}
\label{subsec:3.6.1}

The measurement design follows the ethical framework of Kisteleki~\cite{Kisteleki2016} and the principles of the Menlo Report (2012)~\cite{Bailey2012}:

\textbf{Probe host protection}: All query targets are publicly accessible domains from the Tranco Top 250 corpus. Direct authoritative queries for \ac{A} records are indistinguishable from normal client \ac{DNS} traffic.

\textbf{Infrastructure impact}: With a measurement frequency of one query per domain per day, the pipeline generated at most 50,000 daily queries during the first campaign (250 domains $\times$ 200 probes) and approximately 30,000 during the second (201 domains $\times$ 150 probes). Both figures represent a negligible traffic footprint when contrasted with large-scale production frameworks like OpenINTEL, which processes several hundred million queries daily \cite{vanRijswijk2016}.

\textbf{Transparency}: All measurements are tagged with a project description in RIPE Atlas, allowing authoritative server operators to identify the measurement source. The measurement plan (\texttt{measure\-ments.json}) records all active measurement IDs.

\subsection{Scientific Reproducibility}
\label{subsec:3.6.2}

\textbf{Fixed domain corpus}: The Tranco list identifier recorded in \texttt{tranco\_meta.json} for each measurement week enables exact reproduction of the domain corpus.

\textbf{Measurement traceability}: All RIPE Atlas measurement IDs are recorded in \texttt{measurements.json}. Any researcher with a RIPE Atlas account can retrieve the original raw results using these IDs.

\textbf{Probe set reproducibility}: The pipeline logs the designated probe identifiers along with their corresponding country, \ac{AS} number, and hardware version metadata into a timestamped JSON file formatted as \texttt{selected\_probes\_<date>.json}.

\textbf{Software versioning}: To guarantee full experimental reproducibility, the complete analysis pipeline is hosted publicly at \url{https://github.com/ogautier-unam/dns-measurements}. The accompanying \texttt{require\-ments.\-txt} file locks the exact package versions — including Python 3.11, dnspython, pandas, pyarrow, scipy, and matplotlib — thereby eliminating any environmental or software version ambiguity during third-party replication.

\textbf{Infrastructure reproducibility}: To maintain hardware parity, the project includes a multi-architecture \texttt{Dockerfile} that compiles into a uniform container image. This setup guarantees an identical, deterministic execution environment whether deployed on x86\_64 servers or ARM64 nodes like the Raspberry Pi, allowing seamless pipeline replication directly from source on any supported host.

\subsection{Open Science}
\label{subsec:3.6.3}

In accordance with open science principles, the measurement dataset and the pipeline source code are made publicly available through two complementary channels. The full \ac{DNS} measurement dataset in Parquet format, covering the 127-day campaign (2 April -- 8 August 2026, approximately 4,146,242 results), is deposited on Zenodo~\cite{Zenodo}, a general-purpose open-access repository operated by CERN. The deposit receives a \ac{DOI}, making the dataset permanently citable and independently verifiable, and is released under the Creative Commons CC~BY~4.0 licence. The complete pipeline source code (collection, parsing, and analysis scripts, Dockerfile, and configuration) is published on GitHub at \url{https://github.com/ogautier-unam/dns-measurements} under the MIT licence, providing a versioned, reproducible snapshot of the software used to produce the results.
